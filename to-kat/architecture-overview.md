# Architecture Overview

## What is Dendritic Nix?

Dendritic Nix is an architecture for NixOS configurations built on two ideas:

1. **File placement is wiring** — no manual import lists. Every `.nix` file under `modules/` is automatically discovered via `import-tree`.
2. **Aspects as composable config fragments** — every configuration piece (a program, a system setting, a hardware profile) is an "aspect" that declares what it needs via `includes`.

The framework is provided by [den](https://github.com/denful/den), which gives you:
- `den.aspects.<path>` — a namespace builder that turns file paths into config bundles
- `den.lib.parametric` — composable, overridable configuration tiers (used in quasigod's `styx.workstation`, `styx.laptop`, etc.)
- `den.batteries.*` — utility batteries like auto-hostname detection and user skeleton generation

## How Dendritic Nix Differs from Traditional NixOS Configs

**Traditional**: One giant `configuration.nix`, or a few manually-imported files. Adding a new program means editing an import list AND writing config.

**Dendritic**: A tree of self-contained modules. Adding a new program means dropping a file in the right directory. The tree figures out the rest.

## Comparing quasigod's Config to This Rewrite

This rewrite studies [quasigod's](https://github.com/quasigod) configuration in `reference/quasigod/` and produces a cleaner, more focused system.

| Dimension | quasigod (reference) | This Rewrite (next) |
|---|---|---|
| **Namespace** | Dual (`den` + `styx`) | Single (`den` only) |
| **flake.nix** | Manual, ~30 inputs | Auto-generated via `flake-file`, ~10 inputs |
| **Wiring** | Scattered across modules | Single `dendritic.nix` entrypoint |
| **Host declarations** | Per-file, distributed | Centralized in `hosts/default.nix` |
| **Aspect composition** | Parametric tiers via `styx.workstation`, `styx.laptop`, `styx.desktop` | Flat `includes` list per host |
| **Users** | Inline config in host files | `provides.to-hosts` pattern — defined once, injected everywhere |
| **Channel** | unstable | `nixos-26.05` + `home-manager/release-26.05` |
| **Theming** | catppuccin/nix-colors | stylix + base16 (custom colibri scheme) |
| **Developer DX** | None | `nix run .#vm` test VM + `nh` integration |

### Key Architectural Decision: Flat vs. Parametric Aspects

Quasigod uses `den.lib.parametric.atLeast` to define tiered archetypes:

```nix
# quasigod — parametric tiers
styx.workstation = den.lib.parametric.atLeast {
  includes = [ <styx/boot> <styx/networking> <styx/flatpak> ... ];
};
styx.desktop = den.lib.parametric.atLeast {
  includes = [ <styx/workstation> <styx/ssh/server> ... ];
};
```

This rewrite uses **flat explicit includes** per host:

```nix
# next — explicit flat list
den.aspects.kats-laptop.includes = [
  den.aspects.base
  den.aspects.gui.gnome
  den.aspects.hardware.t480
  ...
];
```

**Why?** Flat lists are easier to trace. You can see exactly what a host includes without bouncing through 3 levels of parametric inheritance. The tradeoff is more repetition — but for 3 hosts, it's worth it.

## The Build Flow

```
flake.nix (auto-generated by flake-file)
  │
  └─ outputs = inputs.flake-parts.lib.mkFlake { inherit inputs; }
       │
       └─ (inputs.import-tree ./modules)   ← auto-imports EVERY .nix under modules/
            │
            ├─ dendritic.nix    ← wiring: den + flake-file + flake inputs
            ├─ defaults.nix     ← applied to ALL hosts/users
            ├─ nh.nix           ← perSystem packages for `nh` CLI
            ├─ vm.nix           ← `nix run .#vm` test VM
            ├─ hosts/
            │   ├─ default.nix  ← entity declarations (which users on which hosts)
            │   ├─ kats-laptop/ ← host-specific aspects
            │   ├─ kats-wsl/
            │   └─ kats-rpi/
            ├─ users/
            │   ├─ ksakura.nix  ← provides.to-hosts → injects user into hosts
            │   └─ kat.nix      ← unprivileged SSH user
            ├─ aspects/
            │   ├─ base/        ← unfree + cli (minimal base every host gets)
            │   ├─ cli/         ← terminal programs (helix, nushell, atuin, etc.)
            │   ├─ gui/         ← graphical (gnome, cosmic, theme, pipewire, xdg)
            │   ├─ hardware/    ← machine-specific (t480)
            │   ├─ networking/  ← networkmanager, openvpn, tailscale
            │   ├─ programs/    ← per-tool aspects (atuin, helium, helix, jujutsu, etc.)
            │   └─ system/      ← kernel, bootloader, fstrim, ssh, tmpfs, zram
            └─ overlays/
                ├─ helium.nix           ← adds helium browser to nixpkgs
                ├─ nil.nix              ← pins nil LSP to a specific revision
                └─ pi-coding-agent.nix  ← adds pi-coding-agent to nixpkgs (used by kats-laptop)
```

### How a Build Happens

1. **`nix run .#kats-laptop`** or **`nix run .#kats-laptop -- switch`**
2. `nh.nix` exposes `den.lib.nh.denPackages` as flake outputs, which `nh` discovers
3. `den` resolves `kats-laptop` → `hosts/default.nix` entity → `den.aspects.kats-laptop` aspect
4. The aspect's `includes` chain pulls in `base` → `cli` → all programs, `gui.gnome`, `hardware.t480`, networking, etc.
5. User config is injected via `provides.to-hosts` from `users/ksakura.nix`
6. `defaults.nix` applies to every host (hostname detection, define-user, homeManager class)
7. The final NixOS + home-manager configuration is evaluated and built

## Host Topology

```
x86_64-linux:
  ├─ kats-laptop  ← ThinkPad T480 (full desktop: GNOME, all programs, hardware support)
  │   users: ksakura (full), kat (SSH-only)
  └─ kats-wsl          ← Windows Subsystem for Linux (minimal CLI)
      users: ksakura

aarch64-linux:
  └─ kats-rpi          ← Raspberry Pi (minimal CLI, headless)
      users: ksakura
```

## Key Design Principles

1. **Single wiring file** — `dendritic.nix` is the only place framework imports and flake inputs are declared
2. **Declarative inputs** — `flake-file.inputs.*.url` inside module files (e.g., `hardware/t480.nix` declares `nixos-hardware`), not in `flake.nix`
3. **Users are host-independent** — defined once, mapped to hosts via `hosts/default.nix`
4. **Aspects are self-contained** — each aspect file = one concern (one program, one system config, one hardware profile)
5. **Overlays declare their own inputs** — `overlays/helium.nix` declares `flake-file.inputs.helium-browser`, so removing the overlay also removes the dependency
