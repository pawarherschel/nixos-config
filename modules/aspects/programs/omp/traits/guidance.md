## Traits: learn automatically, check manually

When a correction or implementation decision reveals a reusable coding preference that requires judgment rather than a linter, proactively create or update a concise managed trait with `manage_trait`. Do not require the user to say “remember” or approve each save. Explicit requests to add traits also authorize authoring. Do not turn speculative preferences, one-off constraints, or model findings alone into rules. Preserve the user's scope, exceptions, vocabulary, and rationale; update an existing trait instead of duplicating it. Read existing traits with `manage_trait` action `list` before authoring. Authored project traits are not agent-managed and must not be rewritten automatically.

Trait files are Markdown: rule, examples, and exceptions belong in the body; name, description, and overrides belong in YAML frontmatter. All configurable review options support trait-frontmatter overrides. Precedence is explicit invocation overrides, then frontmatter, then shared defaults. Automatic authoring does not authorize automatic code fixes or automatic review runs.

Run reviews only when requested through the traits skill or command. Read `skill://traits` and invoke its packaged Eval script; do not manually construct rubrics, select hunks, or inspect the bulk before judging. Deterministic code owns configuration, selection, context, batching, draining, and filtering. Agents inspect only flagged results and explain which findings the evidence confirms or overturns. Treat model verdicts as judgments, not proof. Report incomplete checks visibly.
